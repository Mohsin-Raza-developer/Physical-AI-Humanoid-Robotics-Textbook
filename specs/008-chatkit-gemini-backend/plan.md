# Implementation Plan: ChatKit Backend with Google Gemini Integration

**Branch**: `008-chatkit-gemini-backend` | **Date**: 2025-12-23 | **Spec**: [spec.md](./spec.md)

---

## Summary

Build a production-ready, self-hosted FastAPI backend that integrates OpenAI ChatKit Python SDK with Google Gemini (via OpenAI Agents SDK) to deliver a conversational AI chatbot for the Physical AI & Humanoid Robotics textbook. The backend handles message streaming, agentic tool calling (knowledge base search), thread management, and attachment handling while integrating with existing authentication infrastructure.

**Key Decisions**:
- **LLM**: Google Gemini 2.0 Flash (via AsyncOpenAI adapter)
- **Database**: Neon PostgreSQL (existing auth database, new tables added)
- **Framework**: FastAPI + ChatKit Python SDK + OpenAI Agents SDK
- **Knowledge Tool**: Cohere embed-v4.0 + Qdrant Cloud (existing embeddings)

---

## Phase 1: Data Model & API Contracts

**Status**: ✅ **COMPLETE** (see data-model.md, contracts/api-summary.md)

### Database Schema:

**Tables Created**:
1. **threads**: Conversation threads (thread_id, user_id, title, timestamps)
2. **messages**: Individual messages (message_id, thread_id, role, content, sequence_number)

**Relationships**:
- `users` (existing) → `threads` (1:N, CASCADE DELETE)
- `threads` → `messages` (1:N, CASCADE DELETE)

**Indexes**:
- `threads`: user_id, created_at DESC
- `messages`: thread_id, (thread_id, sequence_number) UNIQUE, created_at
- `attachments`: message_id

**ORM**: SQLAlchemy 2.0+ with async support (asyncpg driver)

### API Contracts:

**Core Endpoints**:
- `POST /api/threads` - Create thread
- `GET /api/threads` - List threads (paginated)
- `GET /api/threads/{id}` - Get thread details
- `DELETE /api/threads/{id}` - Delete thread
- `POST /api/threads/{id}/messages` - Send message (SSE streaming)
- `GET /api/threads/{id}/messages` - Get message history

**Streaming Format**: Server-Sent Events (SSE) with event types:
- `message_start`, `content_delta`, `action_event`, `progress_update`, `widget`, `client_effect`, `message_end`

**Authentication**: JWT Bearer token in Authorization header

**Rate Limiting**: 10 messages/minute, 5 threads/minute, 3 uploads/minute per user

## Risk Mitigation

| Risk | Mitigation Strategy |
|------|---------------------|

| SSE connection drops | Reconnection logic, message persistence |
| Database connection pool exhaustion | Connection pooling config (max 20), monitoring |
| Large message volumes | Pagination, archival strategy |
| Attachment storage costs | File size limits (10MB), retention policy |
| Security vulnerabilities | Input validation, rate limiting, dependency updates |
